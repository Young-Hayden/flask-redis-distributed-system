## 0. 项目一分钟介绍（开场白，背熟）

> "我做了一个小型分布式服务系统，把一个 Flask 学生/新闻管理平台拆成了多个独立进程：Web 主站、爬虫数据接口、WebSocket 聊天、缓存刷新守护进程，互相之间通过 Redis 和 MySQL 解耦协作。部署上做了三件比较有意思的事：一是 nginx 挂了两个 Web 实例做负载均衡，session 迁到了 Redis 实现登录态共享；二是给缓存刷新守护进程实现了 Redis 分布式锁，两个副本同时跑不会重复刷缓存；三是缓存层做了防穿透、防雪崩的改造，并用 Locust 压测验证了缓存的效果。整个项目的配置全部走环境变量，docker-compose 可以一键拉起整套服务。"

面试官想深入哪个词，就展开对应章节。

## 1. 配置外部化（config.py + .env）

**是什么**：所有会因机器而异的参数（MySQL/Redis 地址、密码、各服务端口）集中到 `Code/config.py`，从环境变量读，`.env` 文件兜底，最后才是代码默认值。真实密码在 `.env` 里（被 .gitignore 排除），仓库里只有 `.env.example` 模板。

**为什么**：原来密码 `123456` 硬编码在 `mysql_pool.py` 里，一上传仓库就泄露；分布式部署时 Web 和守护进程可能跑在不同机器上，各自改自己的 `.env`，代码一行不动。

**30 秒讲法**：
> "我把配置做成了三级覆盖：环境变量、.env 文件、代码默认值。这对应 12-Factor App 的第三条——配置存环境。最直接的收益有两个：密码不再进仓库；docker-compose 里 web1、web2 同一份代码，只是环境变量不同——代码零修改就部署到不同容器。"

**追问怎么答**：
- **为什么不直接用 python-dotenv？** 依赖越少越好，20 行的自加载器逻辑（逐行读 `KEY=VALUE`，`setdefault` 不覆盖已有环境变量）更可控，也是练手。
- **SECRET_KEY 为什么必须环境变量？** Flask 用它给 session cookie 签名；硬编码弱密钥 = session 可被伪造登录。随机值兜底的坑我也处理了：`os.urandom` 每次重启都变，所有用户登录态失效，所以生产要在 .env 固定。

## 2. Redis 分布式锁（redis_lock.py）

**是什么**：`Code/redis_lock.py`，用 Redis 实现的跨进程互斥锁。三要素：`SET key token NX EX` 抢锁、随机 uuid token 防误删、Lua 脚本原子"比较再删"。

**为什么**：缓存刷新守护进程部署 2 个副本（高可用）后，两个副本每 5 分钟同一时刻醒来，会抢着删缓存重抓数据——浪费一倍爬虫流量，还可能互相覆盖。单机 `threading.Lock` 只锁本进程，锁必须放在大家都能看到的 Redis 里。

**30 秒讲法**：
> "分布式锁就是'把锁挂在一个所有进程都访问得到的地方'。实现上有三个关键点：抢锁用 `SET NX EX`，一条命令同时保证互斥和过期时间；锁的值存随机 token，释放时只删自己的锁——否则 A 干得慢锁过期被 B 拿走，A 一把删了 B 的锁，互斥就破了；第三，比较 token 和删除必须用 Lua 一步完成，不然'查完是自己、还没删、锁恰好换了主人'这个窗口照样误删。"

**实测证据**（面试可以现场展示）：两个终端同时跑 `redis_listen_wangyi_sina.py`：
```
副本 A：sina_info 缓存刷新完成
副本 B：sina_info 本轮跳过：另一个副本正在刷（分布式锁生效）
```

**追问怎么答**：
- **持有者崩溃了怎么办？** 锁带过期时间（EX），即使进程死了锁也会自动释放，不会永远卡死——这是"自愈"能力。
- **过期了活还没干完？** 锁续期/看门狗：另起协程定期 `EXPIRE` 续命（Redisson 的 watchdog 思路）。我目前的场景刷新最多 15 秒、锁 60 秒，留了 4 倍余量，所以没做续期。
- **Redlock 了解吗？** 单实例 Redis 主从切换瞬间可能丢锁；Redlock 向多个独立 Redis 节点同时抢锁、过半成功才算持有。代价高，一般业务单实例锁 + 过期时间够用。
- **和数据库锁/乐观锁的区别？** Redis 锁性能高但非强一致；数据库锁强一致开销大。我选 Redis 是因为刷缓存本来就是幂等操作，偶尔冲突代价小。

## 3. 缓存三件套改造（cache_utils.py；防击穿的读路径互斥锁另见第 11 节）

**是什么**：把散在各路由里的缓存操作收进 `Code/cache_utils.py`，补了三个生产级要点。

**为什么（三个坑各一句话）**：
1. `keys('stu_info:*')` 是 O(N) 全库扫，百万键时把 Redis 卡死——换成 `SCAN` 游标分批。
2. 缓存全设同一个过期时间 → 大量 key 同一秒集体失效，请求瞬间全砸 MySQL（雪崩）→ TTL 加随机抖动摊开。
3. 查询库里不存在的数据，缓存永远不命中，恶意刷接口全部打穿到数据库（穿透）→ 查无此人也缓存一个空值哨兵 + 短 TTL。

**30 秒讲法**：
> "缓存我做了三件事：SCAN 替代 KEYS，因为 KEYS 是全库扫描会阻塞 Redis；TTL 加随机抖动防雪崩——让 key 的过期时间摊开而不是同一秒集体失效；空值缓存防穿透——查无此人也写一个哨兵值，实测同一个不存在的用户名第二次请求直接返回'用户不存在（缓存拦截）'，根本没碰 MySQL。"

**实测证据**：
```
第一次：curl '/get_name?name=nonexistent999' → 用户不存在          （查库，写入空哨兵）
第二次：curl '/get_name?name=nonexistent999' → 用户不存在（缓存拦截）（被缓存挡住）
```

**追问怎么答**：
- **穿透/击穿/雪崩怎么区分？** 穿透=数据根本不存在；击穿=某个**热点 key 刚好过期**瞬间大量并发回源（解法：互斥锁/逻辑过期）；雪崩=大量 key 同时过期或 Redis 宕机。我的锁+抖动+空哨兵正好各挡一个。
- **缓存和数据库一致性？** 我用 Cache-Aside：先更库再删缓存，另有守护进程定时刷兜底。强一致做不到，业务上接受秒级最终一致；更进一步的方案是延迟双删、binlog 订阅（canal）。
- **为什么不用布隆过滤器？** 布隆过滤器挡"一定不存在"的请求很高效但有误判率且要预维护；小项目空值缓存更简单够用，数据量大时会考虑。

## 4. Redis 共享 Session（flask-session）

**是什么**：`App.py` 里 `SESSION_TYPE='redis'` + `Session(app)`，session 数据从浏览器 cookie 搬到 Redis，cookie 里只剩一个 session_id。

**为什么**：Flask 默认 session 存客户端 cookie（签名防篡改但数据在客户端）。多实例部署后致命：想扩容时 cookie 方案虽不挑实例，但大对象撑爆 cookie、服务端也没法主动踢人下线。放 Redis 后任意实例都能读到同一个登录态，还能直接 `delete` 某个 session 做强制下线。

**30 秒讲法**：
> "多实例部署的前提是服务无状态，而登录态是最典型的状态。我把 session 从 cookie 迁到了 Redis：浏览器只拿一个不透明的 session_id，数据在服务端。这样请求落到哪个 Web 实例都能读到登录态——这就是'分布式 Session'。代价是每次请求多一次 Redis 往返，但 Redis 是内存操作，微秒级，可接受。"

**追问怎么答**：
- **cookie session 和 Redis session 的取舍？** cookie：零服务端存储、简单，但容量 4KB 限制、改密码踢不掉在线、数据暴露（虽签名防篡改但可见）。Redis：可控可扩，代价是引入存储依赖。
- **Redis 挂了登录态全丢？** 是——所以生产要考虑持久化（RDB/AOF）或主从；我演示项目接受这个权衡，同时这也是"依赖越少的存储层越稳"的教训。

## 5. 多实例 + nginx 负载均衡（deploy/nginx.conf）

**是什么**：nginx `upstream web_pool` 轮询 127.0.0.1:5000 和 5001 两个 waitress 实例。

**为什么**：单实例吞吐有上限；无状态 + 负载均衡 = 水平扩容，加机器就能扛更多流量，挂一台流量自动切走。

**30 秒讲法**：
> "我的 Web 服务能水平扩容，靠两个条件：一是应用无状态——状态全在 Redis（session）和 MySQL（数据）里；二是前面有 nginx upstream 轮询分流。加实例只是多起一个进程再往 upstream 里加一行，不用改任何代码。"

**追问怎么答**：
- **轮询/权重/IP哈希/最少连接怎么选？** 默认轮询；服务器配置不均用 weight；会话粘性需求用 ip_hash（但我 session 已共享，不需要粘性）；对响应时间敏感用 least_conn。
- **怎么知道哪个实例挂了？** nginx 被动健康检查（连接失败标记 down 一段时间）；生产可上主动探活。supervisor 负责把挂掉的实例进程拉起来，nginx 负责摘除不接活的——两层保活。

## 6. docker-compose 编排（deploy/docker-compose.yml + Dockerfile）

**是什么**：一份 compose 文件定义 nginx ×1 + web ×2 + 爬虫接口 + WebSocket + MySQL + Redis 共 6 类服务，`docker compose up -d` 一键拉起。

**为什么**：把"分布式部署"从口号变成可复制的动作；同时验证 config.py 的解耦——容器里只改环境变量（`MYSQL_HOST=mysql`），代码零改动。

**30 秒讲法**：
> "compose 里 web1 和 web2 是同一个镜像的两个实例，只有端口环境变量不同；所有服务用服务名互访（MYSQL_HOST=mysql），这验证了我配置解耦的设计。MySQL 首次启动自动执行 schema.sql 建表——基础设施即代码。"

**追问怎么答**：
- **镜像和容器的关系？** 镜像=只读模板（我的三个服务共用一个镜像，只换启动命令）；容器=运行实例。
- **为什么要多进程而不放一个容器里？** 一容器一进程，职责单一、独立伸缩、独立重启；混装会有日志混杂、互相拖死的问题。

## 7. Locust 压测（bench/locustfile.py）

**是什么**：Locust 脚本对比两个场景：点查询命中缓存 vs 每次先删缓存强制回源 MySQL，按名称分开统计。

**实测数据**（50 并发 / 30s / 0 错误）：

| 场景 | 中位延迟 | 平均延迟 |
|---|---|---|
| 点查询_命中缓存 | 5ms | 7ms |
| 点查询_穿透到库 | 8ms | 9ms |

**30 秒讲法（含诚实分析，加分点）**：
> "我压测发现单机小数据集下缓存只快了约 40%，没有想象中十倍差距。分析原因：MySQL 就在本机、表只有几行、查询带索引，回源本身就快——缓存的价值被本地数据库的'快'掩盖了。真实业务里数据库在远端、查询复杂、数据量大，差距会拉开一个数量级；而且缓存的核心价值还有保护数据库这个'最脆弱的共享资源'不被高并发打垮。"

**追问怎么答**：
- **为什么用 Locust 不用 JMeter/ab？** Locust 用 Python 写场景、协程模拟高并发、分布式的 master-worker 扩压测机，脚本即代码能进仓库复现。
- **怎么保证压测有效？** 对照组设计（删缓存强制回源）、多次跑取稳定值、关注 p95/p99 而不是平均值（长尾才是事故来源）。

## 11. 读路径防击穿（cache_get_or_load / cache_list_get_or_rebuild）

**是什么**：缓存三件套补上的最后一块——热点 key 过期的瞬间，N 个并发请求同时 miss、全部冲向 MySQL（击穿）。现在 miss 后先抢 Redis 锁：抢到的请求回源并回填，其余请求短暂等待后重读缓存；回源前还有一次"双重检查"。

**为什么**：守护进程里的分布式锁保护的是"定时刷新"，读路径的 miss 回源是另一个战场——两者都要互斥，但锁的粒度和名字不同（`cache:{key}` / `rebuild:{列表}`）。

**30 秒讲法**：
> "击穿的解法是'只放一个请求去回源'：miss 后先 SET NX 抢锁，抢到的查库回填，没抢到的等 50ms 重读缓存——大概率别人已经填好了。抢到锁后我再查一次缓存（双重检查），因为等锁期间可能已经被回填，不查就会重复回源。至此穿透、击穿、雪崩三件的防护在我代码里闭环了。"

**追问怎么答**：
- **没抢到锁、等完还是没数据怎么办？** 返回空由页面兜底（极端情况），正确性不受影响——宁可短暂降级也不能放 N 个请求同时砸库。
- **为什么不把锁加在 key 过期前（逻辑过期）？** 逻辑过期（value 里存过期时间、永不 TTL）能彻底消灭 miss 窗口，但要改数据结构、代码复杂一档；我的数据量下互斥锁方案已经够用，讲得出取舍即可。

## 12. 登录失败限流（checkFunc.py 的 Redis 计数器）

**是什么**：同一账号 10 分钟窗口内登录失败满 5 次，第 6 次起直接拒绝（不再查数据库）。计数器用 Redis `SET NX EX` + `INCR` 实现。

**为什么**：登录接口不限次数 = 可以无限试密码。限流必须放 Redis 而不是 Python 变量：多实例要共享计数器，且 INCR 是原子的——100 个并发同时 +1 也不丢数。

**30 秒讲法**：
> "我用 Redis 做了个简单的固定窗口限流：失败记在计数器里，`SET NX EX` 先保证键一定带 10 分钟 TTL，再 INCR 原子加一。有个细节——如果反过来先 INCR 再 EXPIRE，两条命令之间进程崩了，计数器就永远不过期，账号被永久锁死。先 SET NX EX 就从顺序上消灭了这个窗口。实测第 6 次请求直接返回'账号已锁定10分钟'。"

**实测证据**：连续 6 次错误密码登录：
```
前 5 次：账号密码错误,请重新登录
第 6 次：失败次数过多，账号已锁定10分钟，请稍后再试
```

**追问怎么答**：
- **按账号限流有什么漏洞？** 攻击者换账号名就绕过了；生产要叠加"IP+账号"双维度（IP 维度防撞库扫号）。
- **固定窗口的边界问题？** 窗口交界处可能放过 2 倍流量（10:00 前 5 次 + 10:00 后 5 次 = 一分钟 10 次）；严格点用滑动窗口（zset 存时间戳）或令牌桶。
- **和 Redis 分布式锁的区别？** 锁是互斥（只允许一个），限流是配额（允许 N 个）——一个是 SET NX 抢占，一个是计数器累减。

## 13. 单元测试 + CI（tests/ + .github/workflows/ci.yml）

**是什么**：16 个 pytest 单测覆盖分布式锁（互斥/防误删/自动过期）、缓存工具（读写往返/TTL 抖动/防穿透/防击穿）、业务函数（分页/限流），push 到 GitHub 后 Actions 自动跑出绿勾。

**为什么**：没有测试的"分布式"项目，面试官没法相信你的锁真的互斥、哨兵真的拦截。测试即证据，CI 即"每次改动都验证"。

**30 秒讲法**：
> "我给三个核心模块写了 16 个单测，全部在真实 Redis 上跑。最有价值的几个断言：锁的'伪造 token 释放必须失败'（防误删）、限流计数器的 TTL 必须存在且不被续期（否则账号永久锁死）、防穿透的 loader 只被调用一次（哨兵生效）。CI 用 GitHub Actions 起一个 Redis service 容器，push 即验证。"

**追问怎么答**：
- **测试为什么不用 mock Redis？** 锁/限流的正确性恰恰依赖 Redis 的原子语义，mock 掉测的就是假逻辑；单测连真 Redis（service 容器）才是集成验证。
- **测试怎么隔离数据？** conftest 里 autouse fixture：用例只写 `test:` 前缀键，跑完自动清，不污染业务缓存。
- **为什么先测这些而不是页面？** 锁/缓存/限流是"写错很难被发现"的逻辑（并发、时序），页面错了肉眼能看见——测试优先保护高风险区。

## 14. 高危问题预警（容易翻车的地方，提前备好）

| 问题 | 危险回答 | 安全回答 |
|---|---|---|
